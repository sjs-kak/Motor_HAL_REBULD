## 2. 这次合并做了什么取舍

规则：**冲突以同事的版本为准**（用户 2026-10-30 明确指定）。以下四处是先按我的判断写过、
后来被推翻、改成他的实现的——不要在后续维护中"修回去"：

### 2.1 `Bsp/Src/bsp_motor_pulse.c` —— 整份换成他的版本（重要）

| | 我先前写的 | 他的（已采用） |
|---|---|---|
| 停车 | 清 CEN/CCxE/MOE，另外加了 `Bsp_MotorPulse_EnsureStopped()` 每圈复查 CEN | 清 CEN/CCxE + TIM1 关 MOE，**逻辑上已不可能有脉冲** |
| 启动 | `StartAll()` 无条件让两侧按旧 PSC 开跑 | `SetFreq(非零)` 只启动**自己那一侧** |
| `Bsp_MotorPulse_Init` | `HAL_TIM_PWM_Start` ×4 再关，中间有出脉冲的窗口 | 不调 `PWM_Start`，直接按停车流程走，上电即静止 |

他注释里点明了真正的病因：`HAL_TIM_Base_Stop` 内部是 `__HAL_TIM_DISABLE`，**在 CCxE 置位时会保留 CEN**。
所以问题在"停表方式"，不在"CEN 被别人抢回去"。

**连带删除**：`Bsp_MotorPulse_EnsureStopped()`（`.h` + `.c`）、三个诊断计数器
（`s_start_cnt`/`s_stop_cnt`/`s_forced_cnt`）、`Bsp_MotorPulse_GetForcedStopCount()`。
`App/Src/motion.c` 里三处调用已一并移除。**现在全工程 0 处引用，这是预期的。**

### 2.2 `Motion_Clamp` 上限 1200 → 5000（`App/Src/motion.c`）

原来卡 `CFG_MOTION_MAX_SPEED_HZ = 1200`，而遥控的 `CFG_RC_MAX_SPEED_HZ = 2500`。
结果：摇杆推到底也只出 1200 Hz，**后半程完全无响应**。

现在统一用 `CFG_PUL_MAX_HZ`（硬件能出的最高频）。理由：两侧最终都落到 `Motion_Move`，
同一套硬件必须同一套上下限。1200 那个保守档降级为"上位机无人值守时的建议值"，不再做硬限幅。

> 这是主管单测抓出来的：9 个失败里有 7 个的根因都是它。

### 2.3 `Motion_Tick` 名字冲突 → 拆成两个

| 名字 | 原型 | 归属 | 职责 |
|---|---|---|---|
| `Motion_Tick` | `void Motion_Tick(void)` | 主线原有 | 上位机命令**掉线看门狗**（`CFG_CMD_TIMEOUT_MS` = 3000 ms） |
| `Motion_SlewTick` | `void Motion_SlewTick(u32 nowMs)` | 他的，已改名 | 遥控的**非阻塞斜坡推进**（每 `CFG_SCURVE_SAMPLE_MS` = 8 ms 推一步） |

C 不支持重载，同名无法共存，所以他的那个改名。`RcControl_Tick` 与单测里的调用点都已同步。

⚠️ `Motion_Tick(void)` 里原来有一句 `if (s_alive_ms == 0) { return; }`，会让遥控斜坡永远推不动
（遥控从不设置 `s_alive_ms`）。现在改成：`s_alive_ms == 0` 时**什么都不做、也不 return**，
掉线判定交给 `RcControl_Tick`（它自己的 `CFG_RC_FRAME_TIMEOUT_MS` = 200 ms，比 3 秒严得多）。

### 2.4 他删掉、我恢复回来的三处（这三处反过来——他没有理由删）

| 文件 | 他删的 | 为什么必须留 |
|---|---|---|
| `Core/Src/main.c` | `Error_Handler()` 里的 `Bsp_Fault_DumpError(caller)` | 进了 `Error_Handler` 就再也看不到串口输出，现场排查失去唯一线索 |
| `Core/Src/stm32f4xx_it.c` | `HardFault_Handler()` 里的 `Bsp_Fault_DumpHardFault(frame)` | HardFault 不输出现场寄存器，复位原因成谜 |
| `Service/Src/protocol.c` | `static volatile u8 s_reading` 与"新帧覆盖旧帧" | 前者防拷贝帧时被中断改缓冲区；后者保证连发命令不丢最后一条 |

另：他把 `u8 Protocol_TakeFrame(...)` 改成了 `u16` 但**漏改头文件声明**，直接编译失败。
`protocol.c` / `protocol.h` 已完整恢复为 `dc82e3b` 版。

`Core/Src/usart.c` 的 `HAL_NVIC_SetPriority(USART1_IRQn, 3, 3)` 也改回了 `(…, 3, 0)`：
`Core/Src/stm32f4xx_hal_msp.c:83` 设的是 `NVIC_PRIORITYGROUP_4`（4 位全做抢占、子优先级必须为 0），
是为后续接 FreeRTOS 的 `configASSERT` 铺路的。他的 `USART3_IRQn, 2, 0` 符合约定，保留。

## 4. 两套遥控方案怎么切换

`Config/Inc/cfg_rc.h` 顶部两个开关，二选一，且有两个 `#error` 防呆：

```c
#define CFG_RC_SOURCE_IBUS 1   /* 同事的 i-BUS（USART3 / PB11）—— 默认 */
#define CFG_RC_SOURCE_PWM  0   /* 主线的 PWM/PPM 捕获（TIM3_CH1 / PA6） */
```

- 关掉的那一支**代码还在，只是不编进来**（`bsp_rc.c` / `app_rc.c` 整体被 `#if` 包住）。
- 切到 PWM 那一支时，`cfg_rc.h` 里 `CFG_RC_*` 宏是**另一套**（他那套是 i-BUS 通道映射，
  主线那套是输入捕获时基/滤波/死区），两套各自在自己的段里，不共存。
- `CFG_RC_DRIVE_ENABLE` 仍为 `0` —— PWM 分支目前只采集、不驱动，且带 `#error` 守卫。

## 5. 未决事项（唯一需要人拍板的）

### 5.1 急停与遥控的优先级

`App/Src/app_init.c` 的 `App_RxByte` 急停分支（`'E'`/`'e'`/`0x1B`）现在是：

```c
Motion_RequestAbort();
Protocol_Reset();
#if (CFG_RC_SOURCE_IBUS != 0)
    Motion_StopImmediate();   /* 把遥控目标一起清零，否则下一圈目标又被设回去 */
#endif
s_estop_hit = 1;
```

实际效果（`Motion_StopImmediate()` 只清速度/目标，**不会**置位 `RcControl` 的禁驾状态）：

| 急停瞬间的摇杆 | 结果 |
|---|---|
| 回中 | 目标算出来是 0，车保持停，状态回到 `RC_STOPPED` |
| 仍推着 | 下一圈 `RcControl_Tick` 重新 `Motion_SetTarget(非0)`，**车会重新动起来** |

两个选项，未定：

- **A（当前实现）**：急停只管上位机命令，遥控始终有效。理由：两个操作者各自独立，
  遥控在场时应保留一条能动的途径。
- **B**：急停一票否决 —— 在上位机收到急停时置一个"遥控禁驾"标志，`RcControl_Tick` 每圈检查，
  置位就强制 `Rc_Stop(RC_DISARMED)`，必须重新上电才能解除。
  理由：按了急停就不该有人能远程把车再推起来。

> 注意：**遥控链路自己掉线**（failsafe / 信号超时）时，`RcControl` 本来就会锁在 `RC_DISARMED`，
> 必须摇杆回中 + CH5 重新拨一遍才能恢复。这条是确定的，与上面 A/B 无关。

### 5.2 上板验证清单（软件层面已无更多可查）

1. 上电看串口是否打印 `BOOT:` 与 `RC: i-BUS USART3 …`（没有 → 先查 PB6/PB7 接线与波特率）
2. 发 `?`，看 `RC … ARMED=1`（`ARMED=0` = 中断没挂上，查 `bsp_uart.c` 的 Rearm；
   `ARMED=1` 但 `age=` 一直增长 = 组帧或 PB11 接线）
3. `RCERR` 不为 0 且持续涨 → 先查线与共地
4. 右摇杆推到底应能到 2500 Hz（若只有 1200，说明 `Motion_Clamp` 又被改回去了）
5. 拔掉接收机电源，200 ms 内四轮必须停
